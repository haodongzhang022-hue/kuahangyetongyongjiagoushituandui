# 路由层设计（0903）· ROUTING_LAYER_0903.md

> 模式：架构师通用团队模式 0903（architect-common-team-0903）
> 机器可读唯一事实源：`registry/industry-registry-0903.json`（本文件是人类可读版，两者必须一致）

## 1. 为什么需要路由层

「一个通用架构师解决所有行业」是不成立的：游戏架构师关心核心循环/数值/性能预算，
金融架构师关心数据真实性/因子/回测/风控，视频创作架构师关心脚本/分镜/成片一致，
小说创作架构师关心世界观/人物/章节节奏，软件开发架构师关心接口/模块/工程规范——
**不同行业的架构差距大于通用部分**。

通用架构师的正确职责是：

1. **维护通用主干**：各行业共享的协作机制（注册表/接力卡/坐标系/门禁通道/run_code/Issue 主干/@ 兜底/记忆）；
2. **持续扩展行业架构师类型**：发现新行业 → 注册新类型 → 建领域包（新增代替修改，只追加不改）；
3. **路由到匹配管线**：任务进来先判行业，再装配「主干 + 领域包」，落到该行业管线执行；
4. **保底高可用**：generic 兜底永存，任何任务都有去处，缺领域包自动降级并留痕。

## 2. 路由判定流程

```
输入诉求
  │  ① 用户显式指定行业 / 显式 @ 领域角色  → 直接命中
  │  ② 关键词表命中（registry 每类型 keywords）→ 命中
  │  ③ 多类型同时命中 → 取第一命中 + note 标注歧义供确认
  │  ④ 未命中 → generic 兜底（禁止无路由硬跑）
  ▼
路由产物 = architect_type + industry + 领域包装配清单
  ▼
写入接力卡 industry / architect_type 字段 → 进入该行业管线
```

执行者：@架构·秘书（入口强制路由）或任一首个接收会话。任何会话不得跳过路由直接开跑。

## 3. 管线装配：主干 + 领域包

| 层 | 内容 | 放哪 | 演进方式 |
|----|------|------|----------|
| 主干（通用骨架） | session/角色/行业注册、run_code、接力卡、坐标系合并、12 角色 @ 兜底、Issue/PR 主干、dev-standard、记忆 | 模式自身（本 persona）+ 0831 同款机制 | 随 0903 版本走 |
| 领域包（行业差异） | knowledge.md 领域知识差异 / pipeline.md 行业管线 / gates.md 行业门禁 / roles.md 行业角色 | `domains/<id>/` | 各领域包独立版本 |

领域包缺失或失效 → 自动降级 generic 主干管线，接力卡留降级痕；禁止在无领域约束下裸跑。

## 5. 新类型注册协议（持续扩展，只追加不改）

1. 触发：路由多次未命中 / 用户提出新行业；
2. 先用 generic 兜底跑通，任务不断链；
3. 建领域包 `domains/<id>/`（可先极简一页，随用随长）；
4. `industry-registry-0903.json` 追加新 id（**只追加、绝不修改旧条目**）；
5. memory 登记 `roster/industry/<id>`；
6. 端到端验证（路由→接力→门禁→交付）通过后 status 置 landed。

## 6. 主干 vs 领域差异的分界原则

- **进主干**：凡各行业都要的机制（注册表/接力卡/坐标系/门禁通道/run_code/Issue 主干/@ 兜底/记忆）；
- **进领域包**：行业特有的事实源/知识/门禁/管线/角色；
- 领域包内发现「几乎所有领域都需要」的机制 → 上提主干评审（同样新增代替修改）。

## 7. 高可用性

1. generic 兜底管线永存、不可退役；
2. 降级链：领域专职 → 混合角色（见 `HYBRID_ROLES_0903.md`）→ generic；降级必须留痕；
3. 主干与领域包隔离演进（版本各自独立，新增代替修改）——单类型故障不影响其他类型与主干；
4. 跨行业任务（1 主域 + 1 副域）主域定管线与门禁，副域转 capabilities_required 走跨行业角色层。
